## 1. 设计结论

动火作业审批采用 **「审批流模板 + 实例快照 + 节点或签/会签」** 模型：

1. **配置态**：安全管理员在后台维护多条**动火审批流模板**；每个模板由有序**审批节点**组成，节点独立配置 **或签（任一通过）** 或 **会签（全部通过）** 及审批人规则。
2. **创建态**：申请人创建动火票时**必须选择**一条已发布的审批流（系统可按动火级别/区域推荐默认项，可改选）。
3. **运行态**：提交审批后按所选模板生成**审批实例**；实例绑定模板版本快照，逐节点推进，全部节点通过后进入「待作业」。
4. **与全生命周期关系**：全生命周期 9 节点中的「审批中」对应本审批流整段执行过程；流程图在审批中阶段可展开显示当前审批节点序号与或签/会签进度。

**一期 M06 现状**：单节点、`approve` 一次即进入 `PENDING_SITE_PERMIT`；本设计为动火专项升级（**Phase C 交付**），需改造作业票 submit/approve 并扩展配置服务模板 API，**不改造**其他票种默认行为。

**服务边界**：模板 CRUD/发布 → **`psm-process-safety-api`**（`configrule`，`:18111`）；审批实例与任务 → **`psm-operation-api`**（`workpermit`，`:18088`）。

## 2. 设计目标

| 目标 | 说明 |
| --- | --- |
| 制度可配置 | 特级/一级/二级动火、不同装置可配置不同审批链，无需改代码 |
| 节点灵活 | 每节点支持或签、会签，满足「分管领导任一审批」与「多专业会签」两类场景 |
| 创建必选 | 动火票创建时选定审批流，避免提交后再临时指定导致审计缺失 |
| 版本可追溯 | 票上固化模板 ID + 版本号 + 快照 JSON，归档可回放当时审批链 |
| 待办清晰 | 或签：多人收到待办，一人处理后其余自动取消；会签：每人独立待办，未签完节点不通过 |

## 3. 概念模型

```text
  psm-config-rule-service                    psm-operation-api
 ┌─────────────────────────┐               ┌─────────────────────────┐
 │ 动火审批流模板           │  创建时选流    │ 动火作业票 work_permit   │
 │ hot_work_workflow_*     │ ─────────────▶│ + template_id/version   │
 └───────────┬─────────────┘               └───────────┬─────────────┘
             │ 1:N                                     │ submit 拉快照
             ▼                                         ▼
 ┌─────────────────────────┐               ┌─────────────────────────┐
 │ 模板节点（或签/会签）     │  提交时实例化  │ permit_approval_*       │
 │ hot_work_workflow_node  │ ─────────────▶│ instance / task / record│
 └─────────────────────────┘               └─────────────────────────┘
```

### 3.1 或签与会签

| 模式 | 编码 | 通过条件 | 待办行为 | 典型场景 |
| --- | --- | --- | --- | --- |
| **或签** | `ANY` | 配置的审批人中 **任意 1 人** 同意 | 多人并行待办；**首个**有效同意后，同节点其余待办自动关闭（CANCELLED） | 分管领导、值班负责人「谁在岗谁批」 |
| **会签** | `ALL` | 配置的审批人 **全部** 同意 | 每人独立待办；仅当全部 APPROVED 后节点通过 | 安全、工艺、设备、电仪多专业会签 |

**节点级驳回/退回**：或签/会签下，**任一**当前节点审批人执行「退回」或「驳回」，整个节点立即结束，按动作进入 `RETURNED` 或 `CLOSED`（与现网一致）；会签场景下其他人待办同步取消。

**节点级转办/加签**：一期动火专项 **不做** 运行时加签/转办，仅在模板配置固定审批人；二期可扩展。

## 4. 审批流模板（配置态）

### 4.1 模板主表字段

| 字段 | 说明 | 校验 |
| --- | --- | --- |
| template_code | 模板编码，如 `DH-L2-STD` | 租户内唯一 |
| template_name | 展示名称，如「二级动火-标准审批」 | 必填 |
| permit_type | 固定 `HOT_WORK` / 动火 | 必填 |
| hot_work_level | 适用动火级别：SPECIAL / LEVEL_1 / LEVEL_2 / ALL | 必填 |
| area_scope | 适用区域：ALL / 指定 area_id 列表 | 可选 |
| version | 版本号，发布自增 | 系统维护 |
| status | DRAFT / PUBLISHED / DISABLED | 仅 PUBLISHED 可被创建时选择 |
| description | 说明 | 可选 |

### 4.2 模板节点字段

| 字段 | 说明 | 校验 |
| --- | --- | --- |
| node_seq | 节点顺序，从 1 开始 | 同模板内唯一、连续 |
| node_name | 节点名称，如「车间主任审批」 | 必填 |
| sign_mode | `ANY` 或签 / `ALL` 会签 | 必填 |
| approver_rule_type | 审批人规则类型（见 4.3） | 必填 |
| approver_rule_value | 规则参数 JSON | 依规则类型 |
| timeout_hours | 超时提醒（小时），0=不提醒 | 可选 |
| required | 是否必经节点 | 默认 true |

### 4.3 审批人规则类型

| 规则类型 | 参数示例 | 解析时机 |
| --- | --- | --- |
| `FIXED_USERS` | `userIds: [101,102]` | 提交时解析为固定用户 |
| `ROLE` | `roleCode: AREA_MANAGER` | 按票上 area_id 解析区域角色持有人 |
| `ORG_POST` | `postCode: SAFETY_SUPERVISOR` | 按组织岗位解析 |
| `FORM_FIELD` | `field: permitIssuerUserId` | 取票上字段（如许可人） |
| `DEPT_LEADER` | `deptFromField: unitId` | 取装置/部门负责人 |

**解析失败**：提交审批时若某节点解析出 0 个审批人 → **阻断提交**，提示「节点【xxx】未找到审批人，请联系管理员」。

**或签/会签人数**：
- 或签：解析出 ≥1 人即可。
- 会签：解析出 ≥1 人；建议配置层限制会签 ≤10 人，超出提示调整规则。

### 4.4 模板发布与变更

- 已发布模板 **不可原地改节点**；变更须复制为新版本或新模板再发布。
- 已在途动火票使用**提交时快照**，不受模板后续变更影响。
- 停用模板：已选该模板的草稿票在提交前须改选其他已发布模板。

## 5. 动火票创建时选择审批流

### 5.1 交互要求

| 步骤 | 要求 |
| --- | --- |
| 创建动火票 | 在基础信息区增加 **「审批流」** 下拉（或卡片选择），**必填** |
| 可选列表 | 仅展示 `permit_type=动火` 且 `status=PUBLISHED` 的模板；可按 `hot_work_level`、`area_id` **过滤推荐** |
| 动火级别联动 | 用户选择特级/一级/二级后，刷新可选审批流列表；无匹配模板时阻断保存并提示 |
| 预览 | 选择后可「预览审批链」：展示节点序号、名称、或签/会签、审批人规则说明（非具体人名） |
| 草稿可改 | `DRAFT` / `RETURNED` 状态下允许更换审批流；**提交后不可更换** |
| 存票字段 | `workflow_template_id`、`workflow_template_version`、可选冗余 `workflow_template_name` |

### 5.2 校验规则

```text
保存/提交动火票
 -> work_type = 动火
 -> hot_work_level 已填
 -> workflow_template_id 已选
 -> 所选模板 permit_type=动火
 -> 所选模板 hot_work_level 匹配（或为 ALL）
 -> 所选模板 area_scope 包含本票 area_id（或为 ALL）
 -> 所选模板 status=PUBLISHED
```

### 5.3 默认推荐逻辑

| 优先级 | 规则 |
| --- | --- |
| 1 | 动火级别 + 区域完全匹配的已发布模板 |
| 2 | 动火级别匹配 + area_scope=ALL |
| 3 | 无匹配 → 不自动选中，强制用户手动选择或联系管理员发布模板 |

## 6. 审批运行时流转

### 6.1 状态关系

```text
[全生命周期]  … → 安全交底签字完成 → 提交审批 → 【审批中】→ 待作业 → …

[审批子流程]  提交
                → 生成 approval_instance（RUNNING）
                → 激活 node_seq=1
                → 解析审批人 → 生成 approval_task（PENDING）
                → 或签：任一人 APPROVE → 节点 COMPLETED → 下一节点
                → 会签：全部 APPROVE → 节点 COMPLETED → 下一节点
                → 无下一节点 → instance COMPLETED → 主票 APPROVING→PENDING_SITE_PERMIT
```

主票 `status` 在整个审批子流程期间保持 **`APPROVING`**；当前审批节点信息存于实例表，供流程图与待办查询。

### 6.2 审批动作

| 动作 | 适用人 | 或签效果 | 会签效果 | 主票状态 |
| --- | --- | --- | --- | --- |
| 同意 APPROVE | 当前节点待办持有人 | 节点通过，其余待办取消 | 仅标记本人已同意；未全员则节点仍进行中 | 末节点通过后 → 待作业 |
| 退回 RETURN | 当前节点待办持有人 | 节点终止，实例 CANCELLED | 同左 | → RETURNED |
| 驳回 REJECT | **任一级**当前节点待办持有人 | 节点终止，实例 CANCELLED | 同左 | → CLOSED（须填驳回原因） |

### 6.3 或签并发控制

- 同一 `approval_task` 组内，采用 **乐观锁 / 数据库条件更新** 保证仅首个 APPROVE 生效。
- 后提交的 APPROVE 返回 409：「该节点已由 xxx 审批通过」。
- 审计仍记录所有点击（含失败尝试，可选）。

### 6.4 会签进度展示

- 节点展示：`2/5 已同意` + 人员列表（已签/待签）。
- 流程图「审批中」子标题：`第 2/4 节点 · 安全部会签（3/5）`。

## 10. 接口设计

### 10.1 配置端（`psm-config-rule-service`，网关前缀 `/api/config`）

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/config/hot-work/workflows` | GET/POST | 模板列表/新建 |
| `/config/hot-work/workflows/{id}` | GET/PUT | 详情/更新草稿 |
| `/config/hot-work/workflows/{id}/nodes` | GET/PUT | 节点维护 |
| `/config/hot-work/workflows/{id}/publish` | POST | 发布（生成 snapshot_json） |
| `/config/hot-work/workflows/{id}/disable` | POST | 停用 |
| `/config/hot-work/workflows/preview-resolvers` | POST | 审批人试算 |
| `/config/hot-work/workflows/{id}/snapshot` | GET | 按 id+version 取快照（作业票服务内部调用） |

### 10.2 动火票业务

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/work-permits/hot-work/available-workflows` | GET | 代理/聚合配置服务：创建页可选已发布模板（level、areaId 过滤） |
| `/work-permits` POST/PUT | | 增加 `workflowTemplateId` 必填（动火） |
| `/work-permits/{id}/submit` | POST | 校验已选流 → 创建 instance → 激活首节点 |
| `/work-permits/{id}/approval/progress` | GET | 审批子流程进度（节点条+会签计数） |
| `/work-permits/{id}/approve` | POST | 改为任务级审批，支持或签/会签逻辑 |
| `/work-permits/{id}/return` | POST | 退回 |
| `/work-permits/{id}/reject` | POST | 驳回 |
| `/work-permits/{id}/approval/tasks` | GET | 当前用户待办任务（可选） |

### 10.3 提交审批核心逻辑（伪代码）

```text
submit(permitId):
  assert permit.workflowTemplateId present
  assert disclosure signed (Phase B)
  run pre-check SUBMIT
  snapshot = loadTemplateSnapshot(templateId, version)
  instance = createInstance(permitId, snapshot)
  activateNode(instance, nodeSeq=1)
  permit.status = APPROVING
```

```text
approve(taskId, opinion):
  task = loadTask(taskId)
  assert task.assignee = currentUser && task.status = PENDING
  node = task.nodeInstance
  if node.sign_mode = ANY:
      mark task APPROVED
      cancel sibling PENDING tasks
      completeNode(node)
  else if node.sign_mode = ALL:
      mark task APPROVED
      if all tasks APPROVED: completeNode(node)
  if has next node: activateNode(next)
  else: completeInstance; permit.status = PENDING_SITE_PERMIT
```

## 12. 异常与边界

| 场景 | 处理 |
| --- | --- |
| 创建未选审批流 | 保存/提交 400，字段级提示 |
| 模板被停用 | 草稿票提交前校验失败，提示改选 |
| 审批人离职/禁用 | 解析时剔除；若节点 0 人则阻断提交 |
| 或签两人同时点同意 | 仅一人成功，另一人 409 |
| 会签一人驳回 | 整票驳回/退回，未签任务取消 |
| 审批中超时 | 按 `timeout_hours` 发提醒，不自动通过 |
| RETURNED 再提交 | 作废旧 instance，按同一模板 **新建** instance 从节点 1 重走 |

## 13. 与全生命周期流程的衔接

| 全生命周期节点 | 本审批流 |
| --- | --- |
| 安全交底签字 | 未完成则 **不允许** submit |

- 外层：`currentPhase = APPROVING`
- 内层：`approvalProgress { currentNodeSeq, totalNodes, signMode, approvedCount, requiredCount }`

## 14. 实施建议（Phase C · 与 A/B 并行）

> **与 Phase A/B 关系**：三条线**并行开发**，不要求 A/B 完成后才启动 C。联调边界见下表；submit 若已接入 Phase B 交底门槛，C3 须一并校验。

| 并行线 | 子阶段 | 服务 | 内容 | 联调依赖 |
| --- | --- | --- | --- | --- |
| Phase A | A | operation + 前端 | `flow-progress`、流程图弹窗 | 可与 C2 并行；审批中展开依赖 C3 |
| Phase B | B | operation + 前端 | 交底签字、待关闭 | 可与 C1/C2 并行 |
| Phase C | C1 | config-rule | 配置库表 + 审批流 CRUD/发布 | 无 |
| Phase C | C2 | config-rule + operation | 创建页选流、available-workflows | 依赖 C1 |
| Phase C | C3 | operation | 实例/任务 + 或签/会签 + approve 改造 | 依赖 C2；与 B 联调 submit |
| Phase C | C4 | operation + 前端 | 待办、审批进度、流程图审批中展开 | 依赖 C3；与 A 联调 flow-progress |

**上线策略**：
- **可分批发布**：C1+C2 可先上「选流」；C3 上多节点审批；A/C4 补齐可视化。
- **切换点**：C3 验收通过后，动火票由 M06 单节点审批切换为多节点或签/会签（可配置开关灰度）。

**建议工期**：C1～C4 与 A/B **同期推进**，整体动火专项约 6～8 周（含联调）；关键路径通常在 C3 submit/approve 与 B 交底门槛汇合处。

## 15. 验收标准

| 编号 | 检查项 |
| --- | --- |
| AC-DH-WF-01 | 动火票创建时未选审批流无法保存/提交 |

| AC-DH-WF-05 | **会签**节点：全部审批人同意后节点才通过 |
| AC-DH-WF-06 | 多节点顺序执行，末节点通过后进入待作业 |
| AC-DH-WF-07 | 退回/驳回后主票状态正确，审批实例 CANCELLED |
| AC-DH-WF-08 | RETURNED 再提交从第一节点重跑 |
| AC-DH-WF-09 | 票上记录 template_id + version，timeline 可展示节点名与或签/会签 |
| AC-DH-WF-10 | 模板发布后修改不影响在途票（快照隔离） |
| AC-DH-WF-11 | 审批人解析为 0 人时提交阻断并提示 |
| AC-DH-WF-12 | 非动火票不强制选动火审批流，行为与现 M06 一致 |
| AC-DH-WF-13 | **首节点或中间节点**审批人驳回后，主票 CLOSED，实例 CANCELLED，须记录驳回原因 |
| AC-DH-WF-14 | 模板数据仅存在于配置服务；作业票库无模板节点表 |
