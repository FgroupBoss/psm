# 技术设计 · 待办聚合与编排

## 1. 定位

待办**不引入**独立「待办状态机」表作为业务事实源，由 BFF 或专用查询服务**只读聚合**各域数据，输出统一 `TodoItem`（与 `MobileTaskVO` 对齐并扩展）。

| 层级 | 组件 | 职责 |
| --- | --- | --- |
| 移动 BFF | `psm-operation-api` → `MobileTaskService` | 现场角色过滤、作业票+报警 |
| Web BFF | `psm-admin-bff`（规划）或 gateway 聚合 | 审批待办 + 全量类型 |
| 审批域 | workflow 服务 | `workflow_task` 持有人与节点状态 |

## 2. 统一 VO（建议）

在 `psm-operation-api` 或公共 API 模块定义，与现有 `MobileTaskVO` 兼容扩展：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| taskType | String | `SITE_PERMIT`、`APPROVE`… |
| bizType | String | `WORK_PERMIT`、`ALARM`… |
| bizId | Long | |
| title | String | |
| status | String | 业务状态快照 |
| priority | String | HIGH/MEDIUM/NORMAL |
| dueAt | Date | |
| actionHint | String | |
| assigneeUserId | Long | 可选 |
| sourceService | String | 排障：work-permit / alarm / workflow |

现有移动 VO 已覆盖 `taskType`、`bizType`、`bizId`、`title`、`status`、`priority`、`dueAt`、`actionHint`。

## 3. 聚合编排

```text
GET /api/mobile/tasks?role=GUARDIAN
        │
        ▼
 MobileTaskService.listTasks()
        ├─ WorkPermitClient.page(status=…)
        ├─ AlarmClient.listPending()
        └─ (N1) WorkflowClient.listPendingTasks(userId)
        │
        ▼
  merge → sort(priority, dueAt) → List<MobileTaskVO>
```

Web 侧建议：

```text
GET /api/workbench/todos
        ├─ 同上移动源
        ├─ WorkflowClient（审批）
        └─ ContractorClient（证书复审，N1）
```

## 4. 各数据源查询规则

### 4.1 作业票（已实现）

| taskType | 查询条件 | 持有人匹配 |
| --- | --- | --- |
| SITE_PERMIT | status=`PENDING_SITE_PERMIT` | `permitIssuerUserId` / 监护人 |
| MONITOR | `IN_PROGRESS`/`SUSPENDED` | `guardianUserId` |
| ACCEPTANCE | `PENDING_ACCEPTANCE` | `supervisorUserId` |

参考：`MobileTaskService` 中 `SITE_PERMIT_STATUSES`、`matchesRole`。

### 4.2 报警（已实现）

- `AlarmClient.listPending(tenantId, limit)`
- `taskType=ALARM_FEEDBACK`

### 4.3 审批待办（N1 规划）

| 项 | 设计 |
| --- | --- |
| 事实表 | `workflow_task`：`instance_id`、`node_id`、`assignee_user_id`、`status=PENDING` |
| taskType | `APPROVE` |
| 或签 | 同节点多人 `PENDING`；一人 `APPROVED` 后其余 `CANCELLED`，聚合时过滤 |
| 会签 | 每人一条待办，直至节点完成 |
| 深链 | `/work-permits/{id}?tab=approval&taskId=` |

审批动作仍由作业票/流程服务完成，BFF **不**代理写操作。

## 5. 与通知的协作

| 时机 | 待办 | 通知 |
| --- | --- | --- |
| 流程进入审批节点 | 查询即出现 | 异步 `send` 模板 `WKP_PENDING_APPROVE` |
| 节点完成 | 查询消失 | 可选结果通知 |

**禁止**：在 BFF 内「创建待办记录」；仅查询。

## 6. 性能与缓存

| 策略 | 说明 |
| --- | --- |
| 分页 | 各源 `pageSize` 上限 50，合并后截断 Top 100 |
| 缓存 | 可选 Redis `todo:{tenant}:{user}` TTL 30s，写操作后不强依赖失效（短 TTL） |
| 降级 | 某一 Client 失败时返回部分列表 + `partial=true` 标志 |

## 7. 接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/mobile/tasks` | GET | 一期已有；参数 `tenantId`、`userId`、`role` |
| `/api/workbench/todos` | GET | Web；参数 `types[]`、分页 |
| `/api/workbench/todos/count` | GET | 分类计数（审批/现场/报警） |

## 8. OA 集成（N3 预留）

| 方向 | 说明 |
| --- | --- |
| 出站 | 平台待办推送至 OA（标题、链接、持有人） |
| 入站 | OA 回调仅作「已读」同步，**不以 OA 状态驱动业务** |
| 冲突 | 业务状态以 PSM 为准，OA 展示延迟可接受 |
