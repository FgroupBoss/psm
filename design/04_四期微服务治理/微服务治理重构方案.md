# 微服务治理重构方案

## 0. 总体结论

### 分析结果

当前后端位于 `code/backend`，是一个 Maven 聚合工程：

- `shared/psm-common-core`：现有公共模块。
- `services/*`：共 25 个 Spring Boot 服务模块。

本次方案按业务类型重新组织服务边界，不再以“技术重复代码”作为合并主线。重复代码仍然需要治理，但它是公共模块抽取问题，不应直接决定业务服务边界。

推荐目标形态：

| 业务类型 | 目标服务 | 纳入服务 | 定位 |
|---|---|---|---|
| 接入与体验层 | `psm-gateway`, `psm-mobile-bff` | gateway、mobile-bff | 网关、移动端编排，保留独立部署 |
| 身份与组织域 | `psm-identity-service` | auth、iam | 登录、用户、角色、权限、SSO |
| 平台支撑域 | `psm-platform-support-service` | master-data、config-rule、file、notification、audit | 基础数据、配置、文件、通知、审计 |
| 实时感知域 | `psm-realtime-perception-service` | alarm、location、video | 报警、定位、视频、门禁、访客、车辆联动 |
| 作业与承包商域 | `psm-operation-control-service` | work-permit、contractor | 作业票、承包商资质、准入、现场作业闭环 |
| 风险防控域 | `psm-risk-control-service` | dual-prevention、major-hazard、inspection | 双防、重大危险源、巡检、隐患/风险闭环 |
| 流程安全域 | `psm-process-safety-service` | moc、pha、pssr、barrier | MOC、PHA、PSSR、屏障/机械完整性 |
| 事件治理域 | `psm-incident-governance-service` | incident、governance、report | 事故、CAPA、治理看板、统计报表 |
| 外部集成域 | `psm-integration-service` | integration | 第三方系统集成，保留独立 |

### 具体操作

治理优先级：

1. 先按业务类型确定目标服务边界。
2. 再抽公共模块与 API 契约，减少合并过程中的复制代码。
3. 最后按业务域逐步合并运行时服务，保留原接口路径和灰度回滚能力。

## 1. 重复代码分析

### 分析结果

重复代码不能作为服务合并的唯一依据，但可以反映服务边界和契约治理问题。

主要重复组如下：

| 重复组 | 文件数量 | 涉及服务 | 业务含义 | 治理建议 |
|---|---:|---|---|---|
| `GlobalExceptionHandler.java` | 24 | 几乎所有服务 | 技术横切能力 | 抽到 `common-web` |
| `AuditChangeLogEntity.java` | 4 | audit、config-rule、iam、master-data | 平台审计能力 | 归入平台支撑域，抽 `psm-audit-api` |
| `AuditChangeLogMapper.java` | 4 | audit、config-rule、iam、master-data | 平台审计能力 | 停止各服务直连审计表，改审计服务 API |
| `EntitySupport.java` | 4 | barrier、moc、pha、pssr | 流程安全域 CRUD 支撑 | 抽公共校验辅助，流程安全域内统一 |
| 作业票 DTO/VO | 约 18 | mobile-bff、work-permit | 作业与承包商域契约 | 抽 `psm-work-permit-api` |
| 报警/承包商/区域检查 DTO | 约 8 | alarm、location、major-hazard、work-permit | 实时感知、作业、风险域协作契约 | 抽 `psm-alarm-api`、`psm-contractor-api` |
| `AlarmServiceClient.java` | 3 | location、major-hazard、video | 实时感知域能力复用 | 归入实时感知域 API |

完全相同类样例：

| 类名 | 涉及服务 | 业务归属 |
|---|---|---|
| `WorkPermitVO.java` | `psm-mobile-bff`, `psm-work-permit-service` | 作业与承包商域 |
| `WorkPermitDetailVO.java` | `psm-mobile-bff`, `psm-work-permit-service` | 作业与承包商域 |
| `GasTestRequest.java` | `psm-mobile-bff`, `psm-work-permit-service` | 作业与承包商域 |
| `AcceptanceRequest.java` | `psm-mobile-bff`, `psm-work-permit-service` | 作业与承包商域 |
| `ContractorEligibilityRequest.java` | `psm-location-service`, `psm-work-permit-service` | 作业与承包商域 |
| `AlarmActionRequest.java` | `psm-alarm-service`, `psm-mobile-bff` | 实时感知域 |
| `AlarmEventVO.java` | `psm-alarm-service`, `psm-mobile-bff` | 实时感知域 |
| `AlarmAreaActiveCheckRequest.java` | `psm-major-hazard-service`, `psm-work-permit-service` | 实时感知域对风险/作业域开放的契约 |

高度相似但不建议直接合并的类型：

| 类型 | 涉及服务 | 判断 |
|---|---|---|
| 状态流转枚举 | work-permit、alarm、moc、pha、pssr、incident | 都是业务状态机，但领域语义不同，只能抽状态校验模式，不能抽统一枚举 |
| 审计实体 | audit、config-rule、iam、master-data | 应统一由审计能力承载，而不是各业务服务复制表结构 |
| Client DTO | alarm、location、major-hazard、work-permit、mobile-bff | 应放入业务 API 契约模块，不放在调用方本地复制 |

### 具体操作

1. 重复异常处理归 `common-web`。
2. 重复审计模型归平台支撑域，审计服务保留独立接口。
3. 作业票与承包商 DTO 归作业与承包商域 API。
4. 报警、定位、视频相关 DTO 归实时感知域 API。
5. 风险、巡检、重大危险源 DTO 归风险防控域 API。

## 2. 按业务类型的服务拆分合理性评估

### 分析结果

评分说明：

- 高：当前服务边界与目标业务域一致，适合保留独立或作为目标域核心。
- 中：业务相关但边界偏窄，适合并入目标业务域。
- 低：更偏技术拆分或聚合查询，独立服务收益有限。

| 当前服务 | 业务类型 | 内聚度 | 独立性 | 变更耦合 | 建议 | 理由 |
|---|---|---:|---:|---:|---|---|
| `psm-gateway` | 接入与体验层 | 高 | 高 | 低 | 保留 | 网关职责明确 |
| `psm-mobile-bff` | 接入与体验层 | 中 | 中 | 高 | 保留但瘦身 | BFF 只做移动端编排，不复制领域 DTO |
| `psm-auth-service` | 身份与组织域 | 高 | 高 | 中 | 合并到 `psm-identity-service` | 与 IAM 强相关 |
| `psm-iam-service` | 身份与组织域 | 高 | 高 | 中 | 合并到 `psm-identity-service` | 用户、角色、权限和认证天然同域 |
| `psm-master-data-service` | 平台支撑域 | 高 | 中 | 高 | 并入平台支撑域或保留为核心模块 | 基础数据支撑所有业务 |
| `psm-config-rule-service` | 平台支撑域 | 中 | 中 | 高 | 并入平台支撑域 | 配置规则是平台支撑能力 |
| `psm-file-service` | 平台支撑域 | 高 | 高 | 低 | 可保留独立部署 | 文件服务边界清晰，合并为可选 |
| `psm-notification-service` | 平台支撑域 | 高 | 高 | 中 | 可保留独立部署 | 通知能力横切，可通过 API 被平台支撑域统一管理 |
| `psm-audit-service` | 平台支撑域 | 高 | 高 | 中 | 可保留独立部署 | 审计是横切能力，数据量与合规要求可能要求独立 |
| `psm-alarm-service` | 实时感知域 | 高 | 高 | 中 | 作为实时感知域核心 | 报警生命周期独立 |
| `psm-location-service` | 实时感知域 | 高 | 高 | 中 | 并入实时感知域 | 定位、门禁、访客、车辆与报警联动强 |
| `psm-video-service` | 实时感知域 | 中 | 中 | 高 | 并入实时感知域 | 视频经常服务报警与定位场景 |
| `psm-work-permit-service` | 作业与承包商域 | 高 | 高 | 高 | 作为作业域核心 | 作业票复杂度高，保留业务核心边界 |
| `psm-contractor-service` | 作业与承包商域 | 高 | 中 | 高 | 并入作业与承包商域 | 承包商资质与作业准入强耦合 |
| `psm-dual-prevention-service` | 风险防控域 | 中 | 中 | 高 | 并入风险防控域 | 与重大危险源、巡检、隐患闭环强相关 |
| `psm-major-hazard-service` | 风险防控域 | 高 | 中 | 高 | 作为风险防控域核心 | 重大危险源是风险管理核心对象 |
| `psm-inspection-service` | 风险防控域 | 高 | 高 | 中 | 并入或保留为风险防控子模块 | 巡检是风险控制执行手段 |
| `psm-moc-service` | 流程安全域 | 高 | 中 | 中 | 并入流程安全域 | MOC 属于流程安全管理 |
| `psm-pha-service` | 流程安全域 | 高 | 中 | 中 | 并入流程安全域 | PHA 属于流程安全分析 |
| `psm-pssr-service` | 流程安全域 | 高 | 中 | 中 | 并入流程安全域 | PSSR 与 MOC/PHA 同属流程安全流程 |
| `psm-barrier-service` | 流程安全域 | 中 | 中 | 中 | 并入流程安全域 | 屏障/机械完整性可作为流程安全控制对象 |
| `psm-incident-service` | 事件治理域 | 高 | 中 | 中 | 并入事件治理域 | 事故、整改、CAPA 需要治理闭环 |
| `psm-governance-service` | 事件治理域 | 中 | 中 | 中 | 并入事件治理域 | 治理看板和任务更适合作为事件治理聚合 |
| `psm-report-service` | 事件治理域 | 中 | 低 | 高 | 并入事件治理域 | 报表是治理结果呈现，不宜独立成为业务域 |
| `psm-integration-service` | 外部集成域 | 高 | 高 | 低 | 保留 | 第三方系统集成适合隔离 |

### 具体操作

按业务类型合并时，优先合并“业务变化一起发生”的服务，而不是优先合并“代码看起来相似”的服务。

## 3. 业务域合并目标方案

### 方案 A：身份与组织域

#### 分析结果

目标服务：`psm-identity-service`

纳入服务：

- `psm-auth-service`
- `psm-iam-service`

职责边界：

- 登录、登出、Token、Session。
- 用户、组织、角色、权限。
- SSO、身份提供方、权限缓存。
- 向网关和业务服务提供统一用户上下文。

收益：

- 认证与权限模型统一。
- 减少网关、前端、后端同时适配两套身份接口。
- 避免用户字段变更时 auth 和 iam 双改。

风险：

- 登录链路风险高。
- Token 兼容、会话续期、权限缓存需要灰度。

#### 具体操作

1. 新服务兼容原 `auth` 与 `iam` API。
2. 网关按接口路径灰度切流。
3. 旧 Token 校验逻辑保留至少一个版本周期。
4. 用户、角色、权限表先不迁移，先合并运行时。

---

### 方案 B：平台支撑域

#### 分析结果

目标服务：`psm-platform-support-service`

纳入服务：

- `psm-master-data-service`
- `psm-config-rule-service`
- `psm-file-service`
- `psm-notification-service`
- `psm-audit-service`

职责边界：

- 基础数据：区域、设备、单位、监测点、字典类主数据。
- 配置规则：业务规则、参数配置、规则评估。
- 文件能力：上传、下载、对象存储访问。
- 通知能力：站内信、短信、消息推送。
- 审计能力：操作日志、变更日志、审计查询。

合并策略：

- 逻辑上归入平台支撑域。
- 物理部署上可分两类：
  - `master-data`、`config-rule` 可优先合并。
  - `file`、`notification`、`audit` 可保留独立部署，但统一 API 契约和版本。

收益：

- 减少基础能力散落导致的重复实现。
- 将审计、通知、文件统一为平台能力，业务域只调用 API。
- 配置规则和主数据变更对业务服务透明。

风险：

- 审计与文件可能数据量大，不宜强行并入一个进程。
- 平台支撑域被过度依赖，需做好限流和降级。

#### 具体操作

1. 先合并 `master-data` 与 `config-rule`。
2. 抽 `psm-audit-api`、`psm-notification-api`、`psm-file-api`。
3. 业务服务停止直接复制审计实体与 Mapper。
4. 文件、通知、审计是否物理合并，按数据量和 SLA 决策。

---

### 方案 C：实时感知域

#### 分析结果

目标服务：`psm-realtime-perception-service`

纳入服务：

- `psm-alarm-service`
- `psm-location-service`
- `psm-video-service`

职责边界：

- 报警事件接入、去重、确认、派发、关闭。
- 人员/车辆/访客定位与门禁事件。
- 视频资源、视频联动、报警联动查看。
- 向风险域和作业域提供区域活跃报警、实时人数、视频联动等查询能力。

收益：

- 报警、定位、视频共享实时上下文。
- 减少 `AlarmServiceClient`、报警区域检查 DTO 的复制。
- 便于统一实时事件模型和告警联动规则。

风险：

- 实时数据吞吐可能高，需要隔离线程池和消息消费。
- 视频能力如果依赖外部平台，故障不能拖垮报警主链路。

#### 具体操作

1. 先抽 `psm-alarm-api` 和 `psm-location-api`。
2. 在目标服务内部保留 `alarm`、`location`、`video` 子包。
3. 报警主链路和视频联动使用独立线程池。
4. 网关保留原服务路径，灰度切到新服务。

---

### 方案 D：作业与承包商域

#### 分析结果

目标服务：`psm-operation-control-service`

纳入服务：

- `psm-work-permit-service`
- `psm-contractor-service`

职责边界：

- 作业票申请、审批、现场确认、气体检测、验收归档。
- 承包商资质、人员资质、准入校验。
- 作业过程与承包商准入闭环。
- 面向移动端提供作业执行 API。

收益：

- 作业票和承包商准入同域，减少跨服务同步校验。
- 删除移动 BFF 对作业票 DTO/VO 的复制。
- 承包商资质变更能直接影响作业准入规则。

风险：

- 作业票是高复杂域，合并承包商后服务体积变大。
- 资质校验可能影响作业票主流程性能。

#### 具体操作

1. 抽 `psm-work-permit-api` 与 `psm-contractor-api`。
2. `mobile-bff` 只依赖 API 契约，不复制 DTO/VO。
3. 承包商准入先通过 API 接入作业票服务。
4. 稳定后再合并运行时服务。

---

### 方案 E：风险防控域

#### 分析结果

目标服务：`psm-risk-control-service`

纳入服务：

- `psm-dual-prevention-service`
- `psm-major-hazard-service`
- `psm-inspection-service`

职责边界：

- 双重预防机制。
- 重大危险源管理。
- 巡检计划、巡检路线、巡检任务。
- 风险点、隐患、检查、整改闭环。

收益：

- 风险识别、重大危险源、巡检执行形成闭环。
- 减少双防、重大危险源、巡检之间的跨服务查询。
- 统一风险对象模型，避免同一区域/风险点多套描述。

风险：

- 巡检任务量可能较大，影响风险管理查询。
- 双防与重大危险源的术语和模型不能强行统一。

#### 具体操作

1. 抽 `psm-risk-api`，统一风险点、区域风险、隐患摘要契约。
2. 合并时保留 `dualprevention`、`majorhazard`、`inspection` 子域包。
3. 巡检调度任务独立线程池。
4. 先合并查询 API，再合并写入流程。

---

### 方案 F：流程安全域

#### 分析结果

目标服务：`psm-process-safety-service`

纳入服务：

- `psm-moc-service`
- `psm-pha-service`
- `psm-pssr-service`
- `psm-barrier-service`

职责边界：

- MOC 变更管理。
- PHA 风险分析。
- PSSR 开车前安全审查。
- 屏障管理、机械完整性。
- 流程安全问题、措施和审批闭环。

收益：

- MOC、PHA、PSSR、Barrier 业务链路天然连续。
- 删除 4 份 `EntitySupport.java` 和重复异常处理。
- 统一流程安全审计和状态流转模式。

风险：

- 各专业域模型差异明显，不能合并为一个“大流程表”。
- 审批状态不能抽成通用枚举，只能抽状态流转接口和测试模式。

#### 具体操作

1. 新服务内部按子域分包：`moc`、`pha`、`pssr`、`barrier`。
2. 共享审批、审计、附件、问题闭环能力。
3. 保留原 API 路径。
4. 数据库先不合并，只合并进程与公共支撑代码。

---

### 方案 G：事件治理域

#### 分析结果

目标服务：`psm-incident-governance-service`

纳入服务：

- `psm-incident-service`
- `psm-governance-service`
- `psm-report-service`

职责边界：

- 事故事件管理。
- CAPA 整改闭环。
- 治理看板。
- 统计报表。
- 安全管理绩效与趋势分析。

收益：

- 事故、整改、治理和报表形成业务闭环。
- 报表不再作为孤立技术聚合服务。
- 治理看板可以直接复用事故/CAPA 领域数据。

风险：

- 报表查询可能拖慢事故处理主链路。
- 报表口径需要版本化管理。

#### 具体操作

1. 报表查询放独立包和独立线程池。
2. 复杂报表优先读缓存、只读库或预聚合表。
3. 事故处理写链路不能依赖报表链路。
4. 原 `report` API 保持兼容。

## 4. 公共模块抽取设计

### 分析结果

公共模块是业务域合并的支撑能力，不替代业务域划分。现有 `psm-common-core` 已经包含基础响应、异常、用户上下文、审计 Client、通知 Client，职责偏宽。

### 具体操作

建议结构：

```text
code/backend/shared/
  psm-common-bom/
  psm-common-core/
  psm-common-data/
  psm-common-web/
  psm-common-feign/
  psm-common-security/
  psm-identity-api/
  psm-platform-api/
  psm-realtime-api/
  psm-operation-api/
  psm-risk-api/
  psm-process-safety-api/
  psm-incident-governance-api/
```

| 模块 | 关键类 | 放置原则 |
|---|---|---|

### 5.1 准备阶段

新增公共模块后执行：


### 5.2 业务域 API 契约抽取

#### 分析结果

跨服务 DTO/VO 应按业务域归属抽取，而不是按调用方归属复制。

#### 具体操作

示例：

```bash
# 在项目根目录执行
git mv code/backend/services/psm-work-permit-service/src/main/java/com/fgroupboss/ai/psm/workpermit/model/vo/WorkPermitVO.java \
       code/backend/shared/psm-operation-api/src/main/java/com/fgroupboss/ai/psm/operation/api/workpermit/vo/WorkPermitVO.java
```

抽取原则：

1. 作业票与承包商契约归 `psm-operation-api`。
2. 报警、定位、视频契约归 `psm-realtime-api`。
3. 风险、重大危险源、巡检契约归 `psm-risk-api`。
4. 审计、通知、文件契约归 `psm-platform-api`。

---

### 5.3 服务运行时合并

#### 分析结果

运行时合并必须晚于 API 契约抽取。先让服务依赖同一 API，再逐步迁移实现代码。

#### 具体操作

每个业务域按以下步骤执行：

1. 新建目标服务模块。
2. 引入对应 `*-api` 模块。
3. 将原服务 Controller 原路径迁入目标服务。
4. 将业务实现按子域包迁移。
5. 数据库连接保持原库或原 schema，不急于合并表。
6. 网关按路径灰度切流。
7. 老服务保留只读或低流量一段时间。
8. 稳定后下线老服务。

服务 POM 示例：

```xml
<dependency>
    <groupId>com.fgroupboss.ai</groupId>
    <artifactId>psm-operation-api</artifactId>
    <version>${psm.common.version}</version>
</dependency>

<dependency>
    <groupId>com.fgroupboss.ai</groupId>
    <artifactId>psm-common-web</artifactId>
    <version>${psm.common.version}</version>
</dependency>
```

## 6. 风险与应对方案

### 业务域过大

#### 分析结果

按业务类型合并后，部分服务会变大，例如风险防控域、平台支撑域。

#### 具体操作

- 先逻辑合并，物理部署可保留拆分。
- 目标服务内部按子域分包。
- 高吞吐链路独立线程池。
- 定时任务、报表、视频联动等非主链路做隔离。

---

### 循环依赖

#### 分析结果

业务域之间如果直接依赖实现模块，会形成循环依赖。

#### 具体操作

- 业务域之间只依赖 `*-api`。
- `common-*` 不允许依赖业务服务。
- 领域 API 只放 DTO、VO、Client interface，不放 ServiceImpl、Mapper、Entity。

---

### 数据库边界不清

#### 分析结果

服务合并不等于立即合库。过早合库会放大事务和回滚风险。

#### 具体操作

- 第一阶段只合并进程，不合并数据库。
- 保留原 schema 和表名。
- 跨原服务事务仍按原边界处理。
- 待运行稳定后再评估表结构收敛。

---

### 报表和实时链路互相影响

#### 分析结果

事件治理域、实时感知域内存在查询重、吞吐高的能力，可能拖慢主业务链路。

#### 具体操作

- 报表查询使用只读库、缓存或预聚合表。
- 实时事件消费使用独立线程池。
- 视频联动失败不能影响报警闭环。
- 网关、服务端均配置限流和超时。

---

### 版本碎片化

#### 分析结果

业务 API 模块增多后，若版本不统一，会出现调用方和提供方契约不一致。

#### 具体操作

- 建 `psm-common-bom`。
- 所有服务通过父 POM 统一版本。
- CI 增加 Maven Enforcer。
- 使用 Renovate 或 Dependabot 做统一升级。

---

## 8. 实际操作步骤

### 8.1 操作总原则

#### 分析结果

本次治理涉及公共模块、API 契约、服务进程、网关路由和数据库边界。为了降低风险，实际执行必须遵循“先契约、后实现；先进程、后数据；先灰度、后下线”的顺序。

#### 具体操作

每个业务域都按以下固定节奏推进：

1. 建立目标服务和目标 API 模块。
2. 抽取跨服务 DTO/VO/Client 到 API 模块。
3. 调用方切换为依赖 API 模块。
4. 目标服务兼容原服务 Controller 路径。
5. 迁移业务实现代码。
6. 网关灰度切流。
7. 保留老服务一段时间。
8. 监控稳定后下线老服务。

每个阶段都必须具备回滚点：

- 代码回滚：回退本次模块迁移提交。
- 路由回滚：网关路由切回老服务。
- 数据回滚：不在第一阶段合库，避免数据库回滚复杂化。

---

### 8.2 第 0 步：建立基线与冻结规则

#### 分析结果

在开始迁移前，需要确认当前工程可构建，并冻结新增重复代码规则。否则迁移过程中会一边抽取、一边新增复制类。

#### 具体操作

在 `code/backend` 目录执行：

```bash
mvn -DskipTests package
```

记录当前模块清单：

```bash
cd code/backend
mvn help:evaluate -Dexpression=project.modules -q -DforceStdout
```

新增团队规则：

- 禁止在 `services/*/src/main/java/**/client/dto` 下复制其他服务 DTO。
- 禁止新增服务本地 `GlobalExceptionHandler.java`。
- 跨服务调用契约必须先进入对应 `shared/*-api` 模块。
- 业务服务之间禁止直接依赖其他服务实现模块。

完成标准：

- 当前主干构建通过，或明确记录当前失败用例。
- 代码评审规则中加入“跨服务 DTO 必须进 API 模块”。
- 后续迁移从一个业务域一个分支开始。

### 8.6 第 4 步：低风险业务域合并

### 8.6.1 身份与组织域合并

#### 分析结果

`auth` 与 `iam` 属于同一个身份与组织域，但登录链路风险高，应先合并运行时，暂不合并数据库。

#### 具体操作

新建目标服务：

```text
services/psm-identity-service
```

迁入包结构：

```text
com.fgroupboss.ai.psm.identity.auth
com.fgroupboss.ai.psm.identity.iam
com.fgroupboss.ai.psm.identity.sso
com.fgroupboss.ai.psm.identity.permission
```

迁移顺序：

1. 复制或迁移 `psm-auth-service` Controller，保留原路径。
2. 复制或迁移 `psm-iam-service` Controller，保留原路径。
3. 合并认证、用户、角色、权限相关配置。
4. 网关新增 identity 路由，但初始流量仍指向老服务。
5. 按路径灰度：先 IAM 查询，再 IAM 写入，最后认证登录。

网关灰度顺序：

| 顺序 | 路径类型 | 风险 |
|---:|---|---|
| 1 | 用户/角色查询 | 低 |
| 2 | 用户/角色写入 | 中 |
| 3 | 权限校验 | 中 |
| 4 | 登录/刷新 Token | 高 |

验证：

```bash
cd code/backend
mvn -pl services/psm-identity-service -am -DskipTests=false test
```

完成标准：

- 原 auth、iam 接口路径兼容。
- 网关灰度后登录、鉴权、权限查询正常。
- 老服务保留可回滚。

回滚方式：

- 网关路由切回 `psm-auth-service` 和 `psm-iam-service`。
- identity 服务停止接流量。

### 8.6.2 作业与承包商域合并

#### 分析结果

作业票与承包商资质、准入校验高度相关，是第二个低风险合并域。合并前必须先完成 `psm-operation-api`。

迁移顺序：

1. `work-permit` 作为核心子域先迁移。
2. `contractor` 以 API 方式接入作业票准入。
3. 将承包商校验从远程调用改为域内调用。
4. `mobile-bff` 保持独立，只依赖 `psm-operation-api`。
5. 网关先切作业票查询，再切作业票写入，最后切承包商准入。

- 移动端作业票接口字段不变。
- 承包商准入校验结果与合并前一致。

回滚方式：

- 网关切回 `psm-work-permit-service`、`psm-contractor-service`。
- 保留原远程承包商 Client 配置一个版本周期。

### 8.7 第 5 步：中风险业务域合并

### 8.7.1 实时感知域合并

#### 分析结果

报警、定位、视频都属于实时感知域，但吞吐和外部依赖差异大，需要做线程池、消息消费和超时隔离。

#### 具体操作

新建目标服务：

### 8.9 第 7 步：网关路由灰度切换

#### 分析结果

服务合并能否低风险落地，关键在于网关按路径切换，而不是一次性替换服务名。

#### 具体操作

每个目标域服务上线时，网关保留原路径：

```text
/api/auth/**        -> psm-identity-service 或 psm-auth-service
/api/iam/**         -> psm-identity-service 或 psm-iam-service
/api/work-permit/** -> psm-operation-control-service 或 psm-work-permit-service
/api/contractor/**  -> psm-operation-control-service 或 psm-contractor-service
```

灰度顺序：

1. 只读查询接口。
2. 低频写接口。
3. 高频写接口。
4. 定时任务和消息消费。
5. 登录、鉴权、报警闭环等高风险链路。

网关切换前检查：

- 新旧接口返回 JSON 字段兼容。
- 新服务健康检查通过。
- 日志包含原业务主键、租户、用户。
- 可一键切回老服务。

完成标准：

- 灰度期间错误率、耗时、日志量无明显异常。
- 下游调用方无需修改接口路径。

---

### 8.10 第 8 步：数据库与任务治理

#### 分析结果

第一阶段禁止合库。服务合并后，数据库可以保持原 schema，通过同一服务内多个数据源或原连接配置访问。

#### 具体操作

数据库治理顺序：

1. 保留原库、原表、原 Mapper XML。
2. 目标服务内按子域配置 Mapper 扫描路径。
3. 跨原服务事务不合并为本地大事务。
4. 稳定一个版本周期后，再评估表归并和索引治理。

定时任务治理：

- 合并前确认每个老服务的定时任务。
- 新老服务并行期间，同一任务只能一侧启用。
- XXL-Job 任务参数中增加目标服务标识。
- 任务切换优先低频任务，再切高频任务。

完成标准：

- 无重复消费。
- 无重复生成巡检、通知、报表、超时任务。
- 数据源配置不进入公共模块。

---

### 8.11 第 9 步：下线老服务

#### 分析结果

老服务不能在网关切流成功后立即删除，应至少保留一个观察周期。

#### 具体操作

老服务下线条件：

- 网关 100% 流量已切到目标服务。
- 监控连续一个版本周期稳定。
- 没有外部系统直接调用老服务地址。
- 定时任务和消息消费已切换。
- 回滚方案经过演练。

下线步骤：

1. 老服务停止接收网关流量。
2. 老服务保留只读或空闲部署。
3. 观察一个版本周期。
4. 删除注册中心实例。
5. 删除部署配置。
6. 最后删除代码模块或改为兼容壳模块。

完成标准：

- 注册中心无老服务生产实例。
- 网关无老服务路由。
- CI 不再构建已下线服务。
- 文档更新目标业务域服务清单。

---

### 8.12 第 10 步：最终验收清单

#### 分析结果

最终验收应覆盖业务域边界、技术重复治理、构建、测试、灰度和回滚。

#### 具体操作

验收清单：

| 检查项 | 完成标准 |
|---|---|
| 业务域边界 | 目标服务按业务类型归属清晰，服务内按子域分包 |

| 定时任务 | 无重复任务、无重复消费 |
| 监控日志 | 关键链路包含租户、用户、业务主键 |
