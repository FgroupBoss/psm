# 基础主数据、权限审计与管理端可操作页开发方案评审稿

## 1. 背景与目标

一期业务模块依赖统一的组织、用户、区域、装置、设备、点位、权限与审计底座。当前仓库已经具备主数据、鉴权、网关、审计和管理端展示骨架，但距离“可操作、可审计、可被业务模块引用”仍有缺口。

本方案目标是在现有代码基础上小步推进，优先交付：

- 基础主数据 CRUD：`org`、`user`、`area`、`unit`、`equipment`、`monitor_point`
- 启用、禁用、软删除、分页、树形查询
- 用户、角色、菜单/API 权限基础模型
- admin-web 从展示页推进到可操作台账页
- 主数据变更审计查询闭环
- 为后续重大危险源模块提供稳定引用对象

## 2. 当前代码现状

### 2.1 后端现状

当前主数据服务位于：

- `code/backend/services/psm-master-data-service`

已有能力：

- `POST /api/master-data/{type}`：新增
- `PUT /api/master-data/{type}/{id}`：编辑
- `POST /api/master-data/{type}/{id}/disable`：禁用
- `DELETE /api/master-data/{type}/{id}`：软删除
- `GET /api/master-data/{type}/{id}`：详情
- `GET /api/master-data/{type}`：分页
- `GET /api/master-data/{type}/tree`：树形查询
- 主数据变更已写入 `audit_change_log`

当前数据模型使用统一表 `master_data_item`：

| 字段 | 用途 |
| --- | --- |
| `tenant_id` | 租户隔离 |
| `category` | 主数据类型 |
| `item_code` | 编码 |
| `item_name` | 名称 |
| `parent_id` | 上级节点 |
| `item_type` | 分类 |
| `status` | 状态 |
| `attributes` | 扩展字段 JSON |
| `deleted` | 软删除 |

鉴权服务已有 `auth_user`、`auth_session`、`auth_identity_provider`、`login_log`。IAM 服务已有 `sys_role_permission`、`sys_role_data_scope`、`sys_api_permission` 雏形，但缺少角色、菜单、用户角色关系等核心模型。

网关已支持：

- `/auth/**` 转发到 auth-service
- `/api/master-data/**` 转发到 master-data-service
- 对受保护接口校验 token 并透传用户上下文请求头

### 2.2 前端现状

当前 admin-web 位于：

- `code/frontend/apps/admin-web`

已有能力：

- 登录
- 恢复当前用户
- 调用主数据分页接口展示区域列表

缺口：

- 无新增、编辑、启用、禁用、删除操作
- 无分页控件、搜索、状态筛选
- 无区域、装置、设备、点位之间的级联选择
- 无审计列表
- 无用户角色权限维护页

## 3. 总体技术路线

### 3.1 第一阶段不拆主数据物理表

建议第一阶段继续使用 `master_data_item + attributes` 的统一主数据表，不立即拆分 `base_area`、`base_unit`、`base_equipment`、`monitor_point` 四张实体表。

理由：

- 当前 CRUD、分页、树形、审计已有可复用实现，继续推进成本最低。
- 一期早期重点是形成可操作闭环，而不是优化复杂查询。
- 区域、装置、设备、点位字段规模可控，适合暂存在 `attributes`。
- 后续重大危险源、报警、作业票出现明确复杂查询压力后，再按热点对象拆表更稳妥。

保留扩展边界：

- 对外接口路径和字段尽量按业务实体设计，不暴露内部统一表实现。
- `category` 固定为业务类型，后续拆表时可保持接口兼容。
- `attributes` 内字段保持规范命名，避免任意 JSON 演变为不可治理结构。

### 3.2 用户模型一期建议扩展 auth_user

一期建议采用：

- `auth_user` 作为唯一登录用户表
- 增加 `org_id`、`post_id` 等组织归属字段
- 新增 `sys_user_role` 绑定用户与角色
- 角色、菜单、API 权限放在 `psm-iam-service`

理由：

- 避免出现 `auth_user` 与 `sys_user` 两套用户 ID。
- 登录态、用户管理、角色绑定链路更短。
- 满足一期权限基础模型，不提前引入复杂身份资料解耦。

后续如需要更复杂的人事档案，可新增 `sys_user_profile`，通过 `auth_user.id` 关联。

## 4. 基础主数据 CRUD 方案

### 4.1 支持类型

扩展 `MasterDataType`，支持以下类型：

| 路径类型 | category | 说明 |
| --- | --- | --- |
| `org` | `ORG` | 组织 |
| `user` | `USER` | 人员台账，短期用于主数据引用 |
| `area` | `AREA` | 区域 |
| `unit` | `UNIT` | 装置 |
| `equipment` | `EQUIPMENT` | 设备 |
| `monitor-point` | `MONITOR_POINT` | 监测点位 |

说明：登录账号仍以 `auth_user` 为准，`user` 类型短期承载人员主数据展示和业务引用。用户权限模型落地后，应收敛为 `auth_user + org_id + sys_user_role`。

### 4.2 通用接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/master-data/{type}` | `POST` | 新增 |
| `/api/master-data/{type}/{id}` | `PUT` | 编辑 |
| `/api/master-data/{type}/{id}/enable` | `POST` | 启用 |
| `/api/master-data/{type}/{id}/disable` | `POST` | 禁用 |
| `/api/master-data/{type}/{id}` | `DELETE` | 软删除 |
| `/api/master-data/{type}/{id}` | `GET` | 详情 |
| `/api/master-data/{type}` | `GET` | 分页查询 |
| `/api/master-data/{type}/tree` | `GET` | 树形查询 |

分页查询参数：

| 参数 | 说明 |
| --- | --- |
| `keyword` | 编码或名称模糊搜索 |
| `status` | 状态筛选，建议新增 |
| `pageNo` | 页码 |
| `pageSize` | 每页数量，最大 200 |

### 4.3 字段设计

通用请求字段：

| 字段 | 说明 |
| --- | --- |
| `tenantId` | 租户 ID，后续应优先取网关上下文 |
| `code` | 编码 |
| `name` | 名称 |
| `parentId` | 上级节点 |
| `type` | 类型 |
| `status` | 状态 |
| `attributes` | 扩展字段 |

各类型扩展字段：

| 类型 | attributes 字段 |
| --- | --- |
| `org` | `orgType`、`sortNo`、`leaderUserId` |
| `user` | `username`、`displayName`、`mobile`、`email`、`orgId`、`postId`、`employmentStatus` |
| `area` | `siteId`、`riskLevel`、`majorHazardFlag`、`sortNo` |
| `unit` | `areaId`、`unitType`、`sortNo` |
| `equipment` | `areaId`、`unitId`、`equipmentType`、`runningStatus` |
| `monitor-point` | `sourceSystem`、`sourceTag`、`metricType`、`unit`、`areaId`、`equipmentId`、`highHigh`、`high`、`low`、`lowLow` |

### 4.4 校验规则

基础校验：

- `tenantId` 必填且大于 0。
- `code`、`name` 必填。
- 同租户、同类型、未删除数据内 `code` 唯一。
- `status` 默认 `ENABLED`。
- `pageSize` 最大限制为 200。

引用校验：

- `parentId` 必须属于同租户、同类型、未删除数据。
- `unit.areaId` 必须引用存在的区域。
- `equipment.areaId` 必须引用存在的区域。
- `equipment.unitId` 必须引用存在的装置。
- `monitor_point.areaId` 必须引用存在的区域。
- `monitor_point.equipmentId` 必须引用存在的设备。

状态规则：

- 禁用对象不允许被新业务引用。
- 第一阶段禁用父级时不自动级联禁用子级，但前端需要提示影响范围。
- 删除采用软删除，不物理删除。

## 5. 权限基础模型方案

### 5.1 数据模型

建议在 `psm-iam-service` 补齐：

| 表 | 说明 |
| --- | --- |
| `sys_role` | 角色 |

| `sys_menu` | 菜单、页面、按钮资源 |

| --- | --- |
| `org_id` | 所属组织 |

### 5.2 权限接口

第一阶段接口建议：

| 接口 | 方法 | 说明 |
| --- | --- | --- |

| `/api/iam/roles/{id}` | `PUT` | 编辑角色 |

后续 `GET /auth/me` 建议返回：

- 用户基础信息

- 角色编码列表
- 权限编码列表
- 菜单树或前端路由资源

第一阶段可以先返回 roles、permissions，不急于做复杂数据权限。

## 6. admin-web 可操作页方案

### 6.1 页面优先级

优先按以下顺序交付：

1. 区域台账：新增、编辑、启用、禁用、删除、分页、搜索
2. 装置台账：复用区域台账组件，增加区域选择
3. 设备台账：增加区域、装置选择
4. 点位台账：增加区域、设备选择和阈值字段
5. 组织、用户基础页
6. 角色权限基础页
7. 审计日志列表页

### 6.2 组件设计

建议抽取：

| 组件 | 说明 |
| --- | --- |
| `MasterDataPage` | 主数据页容器，负责 tab 与数据加载 |
| `MasterDataTable` | 通用列表，支持操作列 |
| `MasterDataFormDialog` | 新增、编辑弹窗 |
| `StatusTag` | 状态显示 |
| `ConfirmAction` | 禁用、启用、删除确认 |

### 6.3 API client 扩展

在 `@psm/api-client` 增加：

- `fetchMasterDataPage`
- `fetchMasterDataTree`
- `createMasterData`
- `updateMasterData`
- `enableMasterData`
- `disableMasterData`
- `deleteMasterData`
- `fetchAuditLogs`

### 6.4 前端交互要求

- 新增和编辑使用弹窗，不跳转页面。
- 禁用、删除必须二次确认。
- 禁用父级节点时提示可能影响下级引用。
- 保存成功后刷新当前页。
- 请求失败展示后端错误信息。
- 表单字段按当前台账类型动态渲染。

## 7. 审计闭环方案

### 7.1 写入范围

主数据以下操作必须写入 `audit_change_log`：

- `CREATE`
- `UPDATE`
- `ENABLE`
- `DISABLE`
- `DELETE`

权限以下操作也需要写入：

- 新增、编辑、启停角色
- 绑定用户角色
- 分配角色权限

### 7.2 查询接口

| 接口 | 方法 | 说明 |

| `/api/audit/logs` | `GET` | 审计日志分页 |

| `tenantId` | 租户 ID，后续优先取上下文 |
| `bizType` | 业务类型 |

| `action` | 操作动作 |
| `operatorName` | 操作人 |

| `endTime` | 结束时间 |
| `pageNo` | 页码 |
| `pageSize` | 每页数量 |

### 7.3 管理端审计列表

列表字段：

- 操作时间
- 操作人
- 动作
- 对象类型
- 对象 ID
- 结果

- 变更前后 JSON 查看

## 8. 网关与安全约束

### 8.1 租户来源

当前接口仍允许前端传 `tenantId`。后续应逐步调整：

- 对受保护接口，优先使用网关透传的 `X-Tenant-Id`。
- 前端传入的 `tenantId` 仅作为兼容参数。
- 当请求头租户和参数租户不一致时，拒绝请求。

### 8.2 操作人来源

主数据和权限变更审计应优先使用：

- `X-User-Id`
- `X-Username`
- `X-Display-Name`

不建议继续依赖前端传 `X-Operator`。

### 8.3 权限拦截

第一阶段先完成模型和接口，API 级权限拦截可分两步：

1. 网关只校验登录态。
2. IAM 权限模型稳定后，网关按 `sys_api_permission + user roles` 做接口权限校验。

## 9. 实施计划

### 9.1 第一批：主数据后端补齐

交付内容：

- 扩展 `MasterDataType`
- 新增 enable 接口
- 分页增加 status 筛选
- 增加 parent 和引用校验
- 审计补充 operatorId、operatorName
- 优先从用户上下文获取 tenantId

完成标准：

- org/user/area/unit/equipment/monitor-point 均可新增、编辑、启停、删除、分页、树形查询。
- 非法引用能返回明确错误。
- 关键变更写入审计。
- `mvn -DskipTests=false test` 通过。

### 9.2 第二批：admin-web 区域台账闭环

交付内容：

- 区域列表搜索、分页
- 新增区域
- 编辑区域
- 启用、禁用、删除
- 错误提示与保存后刷新

完成标准：

- 管理端可完成区域台账全流程操作。
- 操作通过网关访问受保护主数据接口。
- 变更可在审计表中查到。

### 9.3 第三批：复用到装置、设备、点位

交付内容：

- 装置台账
- 设备台账
- 点位台账
- 区域、装置、设备下拉数据联动

完成标准：

- 装置可绑定区域。
- 设备可绑定区域和装置。
- 点位可绑定区域和设备。
- 禁用对象不允许作为新增业务引用。

### 9.4 第四批：权限基础模型

交付内容：

- IAM 核心表补齐
- 角色 CRUD
- 用户绑定角色
- 菜单权限树
- 角色分配权限
- `auth/me` 返回角色和权限

完成标准：

- 用户可绑定一个或多个角色。
- 角色可配置菜单/API 权限。
- 前端能根据权限数据控制入口和按钮。

### 9.5 第五批：审计查询闭环

交付内容：

- 审计分页查询接口
- 管理端审计列表
- 变更前后 JSON 查看

完成标准：

- 主数据和权限变更可按时间、对象、操作人查询。
- 审计记录可追溯到人、时间、对象、变更前后内容。

### 9.6 第六批：进入重大危险源

前置条件：

- 区域、设备、点位台账稳定。
- 点位可被业务模块查询和引用。
- 审计可追溯主数据变更。

进入后优先做重大危险源档案、区域绑定、责任人绑定、点位绑定。

## 10. 风险与处理建议

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 统一表承载复杂业务查询能力有限 | 后续重大危险源、报警可能需要多条件查询 | 一期先用统一表，出现明确查询压力后拆热点表 |
| `tenantId` 由前端传入存在越权风险 | 可能访问其他租户数据 | 逐步改为优先取网关上下文，并校验一致性 |
| `auth_user` 与主数据 user 概念混用 | 权限和业务引用可能混乱 | 一期明确登录用户以 `auth_user` 为准，主数据 user 仅作人员台账过渡 |
| 审计表在 master-data 和 audit-service 均有定义 | 表边界不清 | 查询统一收敛到 audit-service，写入短期保留各服务本地实现 |
| 权限模型一次做太深 | 拖慢主数据闭环 | 先做角色、菜单、API 权限基础模型，复杂数据权限后置 |

## 11. 评审待确认事项

1. 第一阶段是否确认继续使用 `master_data_item + attributes`，暂不拆 `base_area`、`base_unit`、`base_equipment`、`monitor_point` 实体表？
  结论：拆出实体表
2. 用户模型是否确认采用 `auth_user + org_id/post_id + sys_user_role` 作为一期方案？
    结论：确认
3. 主数据接口是否允许从当前的 `/api/master-data/{type}` 继续演进，而不是立即拆成 `/areas`、`/equipments` 等独立接口？
    结论：拆出独立接口
4. 审计查询是否统一归口 `psm-audit-service`？
    结论：是
5. 第一批 admin-web 是否以区域台账为验收样板，再复用到装置、设备、点位？
  结论：是
